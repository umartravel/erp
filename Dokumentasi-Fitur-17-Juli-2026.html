Fitur Baru UMAR CRM — Pendaftaran Publik (Self-Service) & Kotak Masuk Validasi CS

Dokumen ini merangkum seluruh fitur, perbaikan, dan perubahan skema basis data yang dibangun dalam satu sesi pengembangan pada 17 Juli 2026. Ditulis dengan format & gaya yang sama dengan Dokumentasi-Fitur-Baru.html (15 Juli 2026) agar menyatu sebagai bagian dari dokumentasi teknis sistem secara keseluruhan.

Ringkasan Eksekutif

Sesi ini menjawab kebutuhan agar calon jamaah dapat mengisi data pendaftaran sendiri tanpa perlu masuk (login) ke sistem ERP, namun datanya tetap divalidasi manual oleh tim CS sebelum benar-benar tercatat sebagai jamaah aktif. Solusinya adalah alur tiga tahap: Form Publik → Tabel Staging (antrean validasi) → Kotak Masuk internal untuk tim CS Terima/Tolak.

Desain ini secara sengaja tidak langsung menulis ke tabel jamaah produksi — mengikuti prinsip gatekeeper yang sama dipakai pada penguncian harga & kuota paket (lihat §9 Dokumentasi-Teknis.html): data mentah dari internet tidak pernah masuk ke sistem produksi tanpa tinjauan manusia. Saat diterima, sistem menggunakan kembali endpoint POST /api/jamaah yang sudah ada & teruji — bukan menduplikasi logika pembuatan jamaah — sehingga validasi harga/kuota otomatis tetap berlaku.

Seluruh alur telah diuji langsung di browser end-to-end: pengisian form publik, validasi CS (Terima & Tolak), peringatan NIK ganda, serta pengujian khusus terhadap mekanisme rate limiting anti-spam (dikirim 5 request beruntun dari IP yang sama untuk memastikan pembatasan 3x/jam benar-benar aktif). Dua bug nyata ditemukan & diperbaiki selama proses verifikasi (lihat §8).

1. Latar Belakang & Keputusan Desain

Pertanyaan awal yang mendasari fitur ini: "Bagaimana cara calon jamaah mengisi data sendiri tanpa masuk ke sistem ERP, tetapi datanya tetap divalidasi tim CS sebelum masuk ke sistem?" Didiskusikan lebih dulu (tanpa coding) sebelum implementasi dimulai, dan menghasilkan tiga keputusan desain kunci berikut.

1.1 Tabel Staging, Bukan Insert Langsung ke jamaah

Opsi tercepat adalah form publik langsung menulis ke tabel jamaah. Ini ditolak karena melanggar prinsip gatekeeper sistem: harga paket, kuota keberangkatan, dan validitas data (NIK ganda, format salah, spam) harus lolos pemeriksaan sebelum menjadi data produksi. Sebagai gantinya, data publik masuk ke tabel terpisah pendaftaran_publik berstatus Pending, dan hanya berubah menjadi jamaah sungguhan setelah tim CS menekan "Terima".

1.2 Pola Maker-Checker

Sama seperti Expense Report (lihat §1.3 Dokumentasi-Fitur-Baru.html), alur ini memakai pola maker-checker: calon jamaah (maker, tanpa akun) mengisi data mentah; tim CS (checker, admin/sales) memvalidasi & melengkapi data sebelum data tersebut resmi menjadi jamaah.

1.3 DRY — Reuse Endpoint yang Sudah Ada

Alih-alih menulis ulang logika pembuatan jamaah (validasi harga per tipe kamar, pengecekan kuota, dsb.) khusus untuk jalur publik, tombol "Terima" pada Kotak Masuk hanya mengisi otomatis form Pendaftaran Baru yang sudah ada lalu mengirimkannya lewat endpoint POST /api/jamaah yang sudah teruji — dengan tambahan satu parameter opsional source_submission_id untuk penautan balik. Ini menjamin gatekeeper harga/kuota yang sudah ada otomatis berlaku tanpa duplikasi kode (lihat §6).

2. Skema Basis Data

Tabel baru pendaftaran_publik menampung seluruh isian form publik plus metadata proses validasi (siapa yang meninjau, kapan, status, dan tautan ke jamaah hasil "Terima").

db.py — skema tabel staging 
CREATE TABLE IF NOT EXISTS pendaftaran_publik (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    status TEXT DEFAULT 'Pending',
    reviewed_by TEXT, reviewed_at DATETIME, review_note TEXT,
    jamaah_id INTEGER,
    name TEXT, orderer_name TEXT, citizenship TEXT,
    identity_type TEXT, nik TEXT,
    passport_number TEXT, passport_issued TEXT, passport_issuer_city TEXT,
    gender TEXT, birth_place_date TEXT,
    phone TEXT, family_phone TEXT, email TEXT,
    address TEXT, province TEXT, city TEXT, subdistrict TEXT, village TEXT,
    health_history TEXT, mahram TEXT, interest_note TEXT,
    source_ip TEXT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

Kolom status memiliki tiga nilai: Pending (menunggu), Diterima, Ditolak. Kolom jamaah_id baru terisi setelah "Terima" berhasil, menjadi jejak audit yang menghubungkan data staging dengan data jamaah final.

3. Form Publik — /daftar

Halaman baru Pendaftaran-Publik.html, mengikuti pola route publik tanpa autentikasi yang sudah ada (sama seperti /panduan dan /dokumentasi-teknis) — disajikan langsung sebagai FileResponse, tidak melalui SPA utama.

app.py — route publik baru 
@app.get("/daftar")
async def daftar_publik():
    return FileResponse(os.path.join(BASE_DIR, "Pendaftaran-Publik.html"))

Branding (logo & nama perusahaan) dimuat secara dinamis lewat fetch('/api/settings') — sama seperti kop surat PDF pada Expense Report — sehingga halaman ini otomatis mengikuti identitas perusahaan tanpa perlu diubah manual.

Dropdown Provinsi/Kota/Kecamatan/Kelurahan bersifat cascading, memakai API publik emsifa/api-wilayah-indonesia yang sama dipakai form internal Pendaftaran Baru — dipanggil langsung dari browser (tanpa proxy server), dengan atribut data-id pada tiap <option> untuk pencarian jenjang berikutnya.

4. Anti-Spam: Honeypot & Rate Limiting

Karena endpoint ini tanpa autentikasi (harus bisa diakses siapa saja), dua lapis perlindungan sederhana ditambahkan tanpa memerlukan layanan eksternal (captcha pihak ketiga, dsb.).

4.1 Honeypot

Field tersembunyi bernama website disisipkan di form (diposisikan di luar layar lewat CSS, bukan display:none, agar lebih sulit dideteksi bot sederhana). Manusia tidak akan pernah mengisinya; bot yang mengisi semua field secara otomatis kemungkinan besar akan mengisinya juga.

app.py — pemeriksaan honeypot (silent success, tidak memberi tahu bot) 
if g("website"):  # honeypot terisi -> kemungkinan bot
    return {"message": "Data Anda sudah kami terima dan akan diverifikasi tim kami."}

Jika honeypot terisi, sistem tidak menyimpan data apa pun ke database, namun tetap mengembalikan pesan sukses yang sama persis seperti submission asli — agar bot tidak tahu bahwa submission-nya ditolak diam-diam (silent-fail).

4.2 Rate Limiting (3x / Jam / IP)

Dibatasi memakai dictionary in-memory sederhana {ip: [timestamp, ...]} — cukup untuk skala saat ini, tanpa perlu infrastruktur tambahan (Redis, dsb.).

app.py — rate limiter in-memory 
_public_submit_log = {}  # ip -> [timestamp, ...]
RATE_LIMIT_MAX = 3
RATE_LIMIT_WINDOW_SEC = 3600

def _check_rate_limit(ip):
    now = time.time()
    recent = [t for t in _public_submit_log.get(ip, []) if now - t < RATE_LIMIT_WINDOW_SEC]
    if len(recent) >= RATE_LIMIT_MAX:
        _public_submit_log[ip] = recent
        return False
    recent.append(now)
    _public_submit_log[ip] = recent
    return True

Percobaan ke-4 dan seterusnya dalam jendela 1 jam yang sama akan ditolak dengan HTTP 429 beserta pesan Bahasa Indonesia yang ramah. Hasil pengujian nyata mekanisme ini ada di §9.3.

6. Alur "Terima" — Reuse Endpoint Jamaah

Menekan "Terima & Lengkapi Data" pada modal detail akan menutup modal, membuka halaman Pendaftaran Baru, dan mengisi otomatis seluruh field yang tersedia dari data publik. Field yang disengaja tidak diisi otomatis: Status/Pipeline, Agen, Paket, Tipe Kamar, dan Harga — karena keempatnya adalah keputusan yang hanya boleh diambil tim CS, bukan calon jamaah.

public/index.html — acceptSubmission() 
function acceptSubmission(id) {
    const r = inboxCache.find(x => x.id === id);
    closeModal('modal-inbox-detail');
    pendingSubmissionId = id;
    showPage('pendaftaran');
    showToast('Data dari pendaftaran publik sudah diisikan. Lengkapi paket & harga, lalu simpan.');
    const set = (elId, val) => { const el = document.getElementById(elId); if (el && val) { el.value = val; $(el).trigger('change'); } };
    set('reg-name', r.name); set('reg-nik', r.nik); /* ...dst untuk field lain... */
    // Provinsi ditunda sampai data wilayah async selesai dimuat (lihat §8.2)
    (wilayahLoadPromise || Promise.resolve()).then(() => set('reg-province', r.province));
}

Saat form disubmit, payload menyertakan source_submission_id. Di endpoint POST /api/jamaah yang sudah ada, ditambahkan logika penautan balik berikut — dijalankan setelah jamaah berhasil dibuat & gatekeeper harga/kuota lolos:

app.py — penautan balik di dalam jamaah_create() 
source_submission_id = g("source_submission_id")
if source_submission_id:
    sub = db.query_one("SELECT status FROM pendaftaran_publik WHERE id = ?", (source_submission_id,))
    if sub and sub["status"] == "Pending":
        db.execute(
            "UPDATE pendaftaran_publik SET status = 'Diterima', jamaah_id = ?, "
            "reviewed_by = ?, reviewed_at = CURRENT_TIMESTAMP WHERE id = ?",
            (last_id, user["name"], source_submission_id),
        )
        notify("data_updated", "pendaftaran_publik")

Pemeriksaan sub["status"] == "Pending" mencegah double-processing — bila submission yang sama entah bagaimana sudah diproses (misal dua tab CS terbuka bersamaan), penautan kedua tidak akan menimpa hasil yang pertama.

7. Alur "Tolak" & Peringatan NIK Ganda

7.1 Tolak — Alasan Wajib

Tombol "Tolak" memunculkan dialog input alasan. Validasi diterapkan di server (bukan hanya UI) — percobaan tanpa alasan akan ditolak dengan HTTP 400.

app.py 
@app.put("/api/pendaftaran-publik/{pid}/reject")
async def pendaftaran_publik_reject(pid: int, body: dict = Depends(json_body), user=Depends(authenticate_token)):
    require_role(user, "admin", "sales")
    reason = (body.get("reason") or "").strip()
    if not reason:
        raise HTTPException(status_code=400, detail="Alasan penolakan wajib diisi.")
    # ...update status jadi 'Ditolak', simpan review_note, catat log_action REJECT_PUBLIC_REGISTRATION

7.2 Peringatan NIK Ganda

Alih-alih memblokir otomatis pendaftaran dengan NIK yang sudah ada di tabel jamaah (berisiko menolak kasus sah, misal keluarga mendaftarkan dengan NIK admin/pemesan yang sama), sistem hanya menampilkan peringatan visual ke tim CS — keputusan akhir tetap di tangan manusia.

app.py — flag nik_exists dihitung di endpoint list 
existing = db.query_one("SELECT id FROM jamaah WHERE nik = ?", (r["nik"],)) if r["nik"] else None
r["nik_exists"] = bool(existing)

Baris tabel Kotak Masuk menampilkan ikon peringatan (⚠️) di sebelah nama, dan modal detail menampilkan banner kuning bila nik_exists bernilai true.

8. Bug Ditemukan & Diperbaiki Saat Verifikasi

8.1 Kolom "Kota/Kab" Tidak Tersimpan

Saat pengujian pertama (submit data uji dengan Kota "KOTA BOGOR"), modal detail internal menampilkan "Kota/Kab: -". Penyebabnya: baik skema CREATE TABLE maupun statement INSERT pada endpoint submit sama sekali tidak menyertakan kolom city — hanya provinsi, kecamatan, kelurahan, dan alamat yang ditangkap.

Perbaikan: kolom city TEXT ditambahkan ke definisi CREATE TABLE, serta ke ALTER_QUERIES (diperlukan karena tabel sudah lebih dulu dibuat di database development yang sedang berjalan, dengan data uji tersimpan di dalamnya):

db.py — migrasi idempotent untuk database yang sudah berjalan 
ALTER_QUERIES = [
    # ...
    "ALTER TABLE pendaftaran_publik ADD COLUMN city TEXT",
]

Statement INSERT INTO pendaftaran_publik pada app.py turut diperbarui menyertakan city. Diverifikasi ulang dengan submission uji kedua ("Budi Santoso", Kota "KOTA DEPOK") — hasilnya tersimpan & tampil benar.

8.2 Field Provinsi Tertimpa Kosong Setelah "Terima"

Ditemukan saat menguji alur "Terima": provinsi sempat terisi otomatis ("JAWA BARAT"), namun beberapa saat kemudian kembali kosong tanpa interaksi apa pun dari pengguna. Root cause: showPage('pendaftaran') memicu loadWilayah() — sebuah fetch async ke API provinsi yang mengganti total isi elemen <select> provinsi begitu selesai dimuat. Karena acceptSubmission() mengisi field provinsi secara synchronous tepat setelah memanggil showPage() (bukan menunggu fetch-nya selesai), isian tersebut tertimpa balik ke kosong begitu loadWilayah() resolve belakangan.

Perbaikan: promise dari loadWilayah() kini disimpan ke variabel global wilayahLoadPromise, dan pengisian field provinsi menunggu promise tersebut selesai lebih dulu:

public/index.html — before → after (disingkat) 
// Sebelum: set('reg-province', r.province);  // langsung tertimpa oleh loadWilayah() yang masih berjalan

// Sesudah:
if(id === 'pendaftaran') wilayahLoadPromise = loadWilayah();  // di dalam showPage()
// ...
(wilayahLoadPromise || Promise.resolve()).then(() => set('reg-province', r.province));

Diverifikasi dengan memeriksa nilai document.getElementById('reg-province').value setelah jeda 1.5 detik — hasilnya tetap "JAWA BARAT", tidak lagi kosong.

9. Pengujian End-to-End yang Dilakukan

Seluruh pengujian dilakukan langsung di browser (bukan hanya tinjauan kode), memakai data uji nyata yang diisi manual pada form publik maupun panggilan API langsung untuk pengujian rate limit.

9.1 Submit Form Publik & Perbaikan Kota

Dua submission uji dikirim ("Siti Aminah" sebelum perbaikan, "Budi Santoso" sesudah perbaikan) — hasil kedua menunjukkan "Kota/Kab: KOTA DEPOK" tampil benar di Kotak Masuk untuk data yang dikirim setelah perbaikan §8.1.

9.3 Rate Limiting (3x / Jam / IP)

Diuji dengan mengirim 5 request POST /api/public/pendaftaran beruntun dari IP browser yang sama (memakai fetch() langsung, bukan isi form berkali-kali, agar pengujian backend murni tanpa variabel UI):

PercobaanStatus HTTPHasil
1200Diterima (IP ini sudah punya 1 riwayat submit sebelumnya di jam yang sama)
2200Diterima — genap 3 submission dalam jendela 1 jam
3429Diblokir: "Terlalu banyak percobaan dari perangkat ini. Silakan coba lagi nanti."
4429Diblokir
5429Diblokir

Hasil ini mengonfirmasi RATE_LIMIT_MAX = 3 per jam per IP bekerja tepat sesuai desain. Catatan: dua baris data uji ("Test RateLimit 0/1") tercipta di database development akibat pengujian ini — dapat dibersihkan kapan saja karena murni data uji.

9.4 Belum Diuji

Honeypot (perilaku silent-success saat field website terisi) belum diuji langsung di browser pada sesi ini — logikanya sudah diverifikasi lewat tinjauan kode (§4.1), namun pengujian end-to-end via UI belum dilakukan.

11. Catatan & Potensi Pengembangan Lanjutan

  • Field Kota/Kecamatan/Kelurahan pada alur "Terima" sengaja tidak diisi otomatis (hanya Provinsi) karena bersifat cascading dan butuh data API wilayah termuat berurutan — tim CS perlu memilih ulang jenjang di bawah Provinsi secara manual. Bisa ditingkatkan di kemudian hari dengan mengantre pemuatan cascading secara berurutan otomatis.
  • Honeypot belum diuji end-to-end lewat UI browser (baru tinjauan kode) — sebaiknya diuji sebelum fitur ini dianggap sepenuhnya matang secara keamanan.
  • Rate limit memakai dictionary in-memory per-proses — akan reset setiap kali server di-restart, dan tidak akan konsisten bila aplikasi suatu saat dijalankan multi-proses/multi-server. Cukup untuk skala saat ini; perlu dipindah ke penyimpanan bersama (mis. Redis) bila arsitektur berkembang ke multi-instance.
  • Data uji dari pengujian rate limiting ("Test RateLimit 0/1") masih tersimpan di database development — dapat dihapus kapan saja tanpa dampak, murni data pengujian.
