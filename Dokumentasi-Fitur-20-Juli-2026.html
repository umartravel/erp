Fitur Baru UMAR CRM — Detail Jamaah, Refund, & Dokumen Operasional Kafilah

Dokumen ini merangkum seluruh fitur, perbaikan, dan perubahan skema basis data yang dibangun dalam satu sesi pengembangan pada 20 Juli 2026. Ditulis dengan format & gaya yang sama dengan Dokumentasi-Fitur-17-Juli-2026.html agar menyatu sebagai bagian dari dokumentasi teknis sistem secara keseluruhan.

Ringkasan Eksekutif

Sesi ini melanjutkan pengerjaan "Penyempurnaan Database Jamaah" dari rencana pengembangan: dimulai dari modal Detail Lengkap Jamaah (ringkasan read-only + riwayat pembayaran), berkembang menjadi alur Refund penuh bergaya maker-checker-approver (CS ajukan → Manajemen setujui → Finance cairkan), perbaikan audit trail pada Edit Data Jamaah, dan berpuncak pada tiga dokumen PDF operasional (Manifest, Roomlist, Absensi) untuk tim Ops — dirancang langsung berdasarkan contoh dokumen hardcopy yang sudah dipakai perusahaan.

Beberapa keputusan desain penting diambil bersama pengguna sebelum coding: refund dipisah dari alur Batalkan Booking namun bisa memicu pembatalan otomatis hanya saat dana benar-benar dicairkan (bukan saat diajukan/disetujui); pengelompokan kamar Roomlist dibuat otomatis (kasar) lalu bisa diedit manual staff sebelum dicetak; dan field tanggal lahir dipecah permanen menjadi birth_place + birth_date agar usia jamaah bisa dihitung akurat di Manifest.

Seluruh fitur telah diuji langsung di browser & via PDF yang diunduh — termasuk skenario pengujian bertahap (DP → cicilan → lunas → refund sebagian → pembatalan otomatis) dan perbandingan visual PDF hasil generate terhadap 3 dokumen referensi asli yang diberikan pengguna.

1. Modal Detail Lengkap Jamaah & Riwayat Pembayaran

Sebelumnya, melihat "gambaran utuh" satu jamaah berarti membuka 5 modal terpisah (Aktivitas, Komentar, Document Vault, Kelengkapan Dokumen, Edit) satu per satu. Modal baru ini menjadi ringkasan read-only terpusat, dengan tombol pintasan ke modal-modal tersebut agar aksi tulis tetap lewat jalur yang sudah teruji — tidak menduplikasi logika.

1.1 Struktur Modal

Dipicu tombol mata (👁️) di kolom Aksi & Kolaborasi, halaman Database Jamaah. Seluruh data (kecuali riwayat pembayaran) diambil langsung dari allJamaah yang sudah dimuat di client — tidak perlu endpoint baru untuk kontennya sendiri.

1.2 Riwayat Pembayaran — Label Bertahap Otomatis

Endpoint baru GET /api/jamaah/{id}/payments mengambil transaksi kategori payment dari Buku Kas, urut kronologis. Frontend menghitung label tiap entri berdasarkan akumulasi terhadap total_price:

public/index.html — logika label di openJamaahDetail() 
const label = paymentSeq === 1
    ? (isFinal ? 'Pembayaran Lunas (Sekaligus)' : 'DP (Pembayaran ke-1)')
    : `Pembayaran ke-${paymentSeq}`;
// isFinal = cumulative >= total_price -> tampil badge LUNAS

Diuji dengan skenario 3 tahap (DP Rp 5jt → cicilan Rp 3jt → pelunasan Rp 17,9jt) — label tampil tepat "DP (Pembayaran ke-1)" → "Pembayaran ke-2" → "Pembayaran ke-3 [LUNAS]", dan status jamaah otomatis ikut berubah jadi "Lunas".

2. Refund — Maker-Checker-Approver

Sebelum fitur ini, "Batalkan Booking" sama sekali tidak menyentuh uang — paid_amount tetap tercatat penuh meski jamaah batal, membuat Saldo Kas Aktif berpotensi salah. Refund dirancang terpisah dari pembatalan (karena tidak semua refund berarti batal — kadang cuma penyesuaian harga), dengan opsi eksplisit untuk menyatukan keduanya bila memang diperlukan.

2.1 Tabel & Alur Status

db.py — skema refund_requests 
CREATE TABLE IF NOT EXISTS refund_requests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    jamaah_id INTEGER, amount INTEGER, reason TEXT,
    status TEXT DEFAULT 'Pending',
    requested_by TEXT, requested_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    approved_by TEXT, approved_at DATETIME, reject_reason TEXT,
    disbursed_by TEXT, disbursed_at DATETIME, transaction_id INTEGER,
    cancel_booking INTEGER DEFAULT 0
);

Pending

CS / Sales

Ajukan nominal (bisa sebagian) + alasan wajib, dari tombol "Ajukan Refund" di modal Detail Jamaah.

Disetujui

admin, management

Keputusan bisnis: refund ini legitimate. Belum ada uang bergerak di titik ini.

Dicairkan

admin, finance

Hanya bisa dari status Disetujui. Mencatat transaksi expense, mengurangi paid_amount, dan (bila dicentang) baru di titik ini membatalkan booking.

2.2 Kenapa Pembatalan Menunggu Pencairan (Bukan Persetujuan)?

Checkbox "Sekaligus batalkan booking ini" tersedia saat CS mengajukan. Tapi pipeline_stage baru benar-benar diubah jadi Cancelled saat Finance mencairkan dana — bukan saat diajukan atau disetujui — supaya status booking selalu mencerminkan kondisi uang yang sungguhan, bukan rencana yang masih bisa gagal di tengah jalan.

app.py — refund_request_disburse() 
if r["cancel_booking"] and jamaah["pipeline_stage"] != "Cancelled":
    db.execute(
        "UPDATE jamaah SET pipeline_stage = 'Cancelled', cancel_reason = ? WHERE id = ?",
        (r["reason"], jamaah["id"]),
    )

Diuji end-to-end: refund Rp 5jt dengan checkbox aktif → status jamaah tetap "DP Masuk" setelah diajukan maupun disetujui Manajemen → baru berubah jadi "Cancelled" tepat saat Finance klik "Cairkan Dana", dengan cancel_reason otomatis terisi dari alasan refund.

3. Audit Trail — Edit Data Jamaah

Sebelumnya PUT /api/jamaah/{id} mencatat log generik ("Update profil jamaah NIK: ...") tanpa menyebut apa yang sebenarnya berubah — dan jalur "profil terkunci" (edit non-admin saat sudah ada DP) tidak tercatat audit sama sekali.

app.py — deteksi perubahan field per field 
def _field_change(label, old_val, new_val):
    old_val, new_val = old_val or "-", new_val or "-"
    return f"{label} ({old_val} → {new_val})" if old_val != new_val else None

Hasil log kini hanya menyebut field yang benar-benar berubah, contoh nyata dari pengujian:

Update data jamaah Budi Santoso: No. WA (089999888777 → 089876543210);
Total Harga (Rp 25.900.000 → Rp 20.000.000) [Keterangan: Uji: nego harga khusus, diskon Rp 5.9jt dari harga normal]

Perubahan Total Harga kini wajib disertai keterangan — divalidasi server (bukan hanya UI): if new_price != old_price and not price_change_note: raise HTTPException(400, ...). Field "Keterangan Perubahan Harga" di form Edit Jamaah otomatis muncul hanya saat nominal harga diubah.

4. Dokumen Operasional: Manifest, Roomlist, Absensi

Dirancang berdasarkan 3 dokumen hardcopy nyata yang sudah dipakai perusahaan (diberikan pengguna sebagai referensi), lalu dipetakan ke data yang ada di sistem. Dibangkitkan server-side dengan reportlab (modul baru jamaah_docs_pdf.py) — bukan trik window.print() — supaya hasil konsisten & layak diarsipkan.

4.1 Pemisahan Tanggal Lahir (Prasyarat Manifest)

Manifest referensi butuh kolom POB, DOB, dan AGE terpisah — sementara sistem sebelumnya menyimpan birth_place_date sebagai satu string bebas ketik ("Depok, 12 Januari 1985"). Dipecah permanen jadi birth_place + birth_date (tanggal asli) di tabel jamaah & pendaftaran_publik, menyentuh form Pendaftaran Baru, Pendaftaran Publik, Edit Jamaah, dan modal Detail Jamaah. Data lama tidak dimigrasikan otomatis (format bebas ketik terlalu tidak konsisten untuk diparsing aman) — kolom baru kosong sampai diisi ulang.

jamaah_docs_pdf.py — usia dihitung relatif terhadap tanggal keberangkatan paket 
def _calc_age(birth_date, as_of=None):
    bd = datetime.datetime.strptime(str(birth_date)[:10], "%Y-%m-%d").date()
    ref = as_of or datetime.date.today()
    return ref.year - bd.year - ((ref.month, ref.day) < (bd.month, bd.day))

4.2 Manifest Jamaah

Tabel identitas & paspor lengkap per paket (GET /api/packages/{id}/manifest-pdf) — Nama, Gender, Hubungan, Tempat/Tgl Lahir, Usia, No. Paspor, Tgl Terbit/Habis, Kantor Penerbit. Diverifikasi: usia terhitung tepat relatif terhadap tanggal keberangkatan (mis. lahir 15 Nov 1975, per 24 Mar 2026 → 50 tahun, karena ulang tahun belum lewat di tahun berjalan).

4.3 Roomlist & Pengelompokan Kamar Otomatis

Alih-alih mengandalkan field room_number bebas ketik yang tidak konsisten, sistem mengelompokkan otomatis jamaah per gender + tipe kamar (kapasitas: QUAD=4, TRIPLE=3, DOUBLE=2, QUINT=5), diberi label urut ("QUAD 1 (LAKI-LAKI)", dst).

jamaah_docs_pdf.py — auto_group_rooms() 
for (key, gender), members in buckets.items():
    capacity = ROOM_CAPACITY[key]
    for idx, chunk_start in enumerate(range(0, len(members), capacity), start=1):
        chunk = members[chunk_start:chunk_start + capacity]
        label = f"{key} {idx} ({gender_label})"

Karena pengelompokan kasar tidak bisa menebak kasus keluarga campur gender atau penyisipan Tour Leader/Muthawif, disediakan modal "Atur Kelompok Kamar" (halaman Logistik & Ops) — staff bisa mengedit label kelompok tiap jamaah secara manual sebelum menyimpan & mencetak. Tour Leader/Muthawif (dari packages.tour_leader/mutawwif) ditampilkan sebagai baris info terpisah di bawah tabel Roomlist, bukan disisipkan interaktif ke kelompok tertentu — simplifikasi yang disengaja karena keduanya bukan data jamaah (tanpa NIK/gender tersimpan).

Diuji: 4 jamaah laki-laki otomatis masuk "QUAD 1 (LAKI-LAKI)", 2 jamaah perempuan masuk "QUAD 1 (PEREMPUAN)"; edit manual satu jamaah ke label kelompok custom berhasil tersimpan tanpa mengubah jamaah lain. PDF hasil generate dibandingkan visual terhadap dokumen referensi — sel kamar tergabung (merged) persis seperti aslinya.

4.4 Absensi Jamaah & Ceklist

Daftar nama + kolom checklist (Keberangkatan/Tiba Madinah/Tiba Mekkah/Kepulangan) + beberapa kolom kosong tambahan untuk Tour Leader menulis checkpoint lain secara manual saat perjalanan — mengikuti struktur dokumen referensi asli.

4.5 Titik Akses

Tiga tombol baru di halaman Logistik & Ops ("Manifest PDF", "Atur Kelompok Kamar", "Absensi PDF"), berdampingan dengan tombol cetak lama yang tidak diubah — semua memakai selector paket yang sama.

6. Catatan & Potensi Pengembangan Lanjutan

  • Tour Leader/Muthawif belum bisa disisipkan interaktif ke kelompok kamar tertentu di modal "Atur Kelompok Kamar" — saat ini hanya tampil sebagai baris info terpisah di PDF Roomlist. Bila perlu digabung ke kelompok tertentu, butuh penyimpanan tambahan (mis. kolom gender staf) yang saat ini tidak tersimpan.
  • Data tanggal lahir lama (kolom birth_place_date gabungan) tidak dimigrasikan otomatis ke birth_place/birth_date — jamaah lama akan tampil "-" pada Manifest sampai datanya diisi ulang manual.
  • Sempat dicoba mengubah field "Tempat Lahir" jadi dropdown Provinsi+Kota Lahir (cascading, mengikuti API wilayah) atas permintaan pengguna, namun dikembalikan ke teks bebas setelah diuji — dianggap kurang perlu untuk saat ini.
  • Rate limit & validasi refund saat ini hanya mengecek total pengajuan Pending+Disetujui terhadap paid_amount — belum menangani kasus jamaah mengubah total_price di tengah proses refund berjalan.
