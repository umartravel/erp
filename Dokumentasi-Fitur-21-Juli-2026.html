Fitur Baru UMAR CRM — Fee Komisi per Paket, Migrasi Data Agen, & Pendaftaran Mitra Publik

Dokumen ini merangkum seluruh fitur, perbaikan, dan perubahan skema basis data yang dibangun dalam satu sesi pengembangan pada 21 Juli 2026. Ditulis dengan format & gaya yang sama dengan Dokumentasi-Fitur-20-Juli-2026.html agar menyatu sebagai bagian dari dokumentasi teknis sistem secara keseluruhan.

Ringkasan Eksekutif

Sesi ini menuntaskan diskusi Fee Komisi Agen yang dimulai hari sebelumnya: model fee dibalik dari default per-agen menjadi default per-paket, dengan pengecualian per kombinasi (agen, paket) tetap tersedia sebagai lapisan override di atasnya. Rencana fitur "cashback agen referral" (agen membawa agen lain) yang sempat didiskusikan dibatalkan oleh pengguna dan akan ditangani lewat fitur Expense Report yang sudah ada — bukan bagian dari sesi ini.

Sesi kemudian bergeser ke persiapan migrasi data Keagenan: pengguna membagikan link Google Form & Google Sheet ("MASTER DATA KONSULTAN UMAR") berisi ratusan data konsultan/agen historis. Setelah analisis struktur sheet, tabel agents diperluas mengikuti field-field yang ditemukan (alamat lengkap, Instagram, email, nomor surat perjanjian, checklist kelengkapan marketing kit), dan dibangun form pendaftaran agen publik (/daftar-agen) beserta alur review-nya — meniru persis pola maker-checker yang sudah teruji pada pendaftaran jamaah publik. Impor data historis dari Google Sheet itu sendiri belum dijalankan — baru strukturnya yang disiapkan, sesuai arahan eksplisit pengguna ("untuk impor nya nanti").

Seluruh fitur diuji langsung di browser: perbaikan bug harga paket (lanjutan dari sesi sebelumnya) diverifikasi lewat klik UI asli (bukan hanya panggilan API), dan alur pendaftaran agen diuji end-to-end mulai dari mengisi form publik → muncul realtime di Kotak Masuk → diterima lewat modal pre-filled (termasuk alamat cascading 4 jenjang) → tersimpan utuh di tabel agents → diverifikasi lagi tetap utuh setelah dibuka ulang lewat Edit Agen.

1. Fee Komisi Berbasis Paket

Model sebelumnya menyimpan satu commission_fee per agen sebagai default, dengan tabel agent_package_fees sebagai pengecualian per (agen, paket). Pengguna menunjukkan bahwa ini terbalik secara bisnis: setiap paket yang mempunyai fee komisi berbeda-beda, dan agen baru seharusnya otomatis mengikuti fee paket yang dipilih — bukan sebaliknya. Setelah didiskusikan, model dibalik namun pengecualian per (agen, paket) yang sudah ada (dibangun sesi sebelumnya) tetap dipertahankan sebagai lapisan override.

1.1 Urutan Pencarian Fee (Lookup Precedence)

app.py — jamaah_payment(), saat status berubah ke Lunas 
package_fee = db.query_one(
    "SELECT commission_fee FROM agent_package_fees WHERE agent_id = ? AND package_name = ?",
    (jamaah["agent_id"], jamaah["package_type"]),
)
fee = package_fee["commission_fee"] if package_fee else (jamaah["default_commission_fee"] or 0)

Urutannya: cek pengecualian spesifik (agen, paket) dulu → kalau tidak ada, jatuh balik ke fee default milik paket itu sendiri (packages.default_commission_fee). Kolom agents.commission_fee lama dibiarkan ada di skema (tidak di-DROP, mengikuti konvensi "jangan pernah hapus kolom lama" yang dipakai konsisten di seluruh sistem ini) tapi sudah tidak dibaca/ditulis oleh kode manapun.

1.3 Bug Ditemukan & Diperbaiki: Harga Paket Ter-wipe ke NULL

Saat menguji fitur ini via panggilan API langsung, ditemukan bug nyata: endpoint PUT /api/packages/{id} menulis ulang kolom price (harga umum lama, sebelum ada rincian per tipe kamar) secara tanpa syarat dari payload — padahal modal Edit Paket tidak punya input field untuk price. Setiap kali admin mengedit paket lewat UI, harga paket akan senyap menjadi NULL, merusak validasi gatekeeper harga saat pendaftaran jamaah baru.

app.py — packages_update(), sebelum vs sesudah perbaikan 
# `price` (harga umum lama) sengaja TIDAK disentuh -- tidak ada field untuk itu
# di form Edit Paket, jadi kalau ikut ditulis ulang akan selalu jadi NULL.
db.execute(
    "UPDATE packages SET name = ?, departure_date = ?, duration = ?, quota = ?, "
    "price_quad = ?, price_triple = ?, price_double = ?, default_commission_fee = ? WHERE id = ?",
    (g("name"), g("departure_date"), g("duration"), quota, g("price_quad"),
     g("price_triple"), g("price_double"), fee, pid),
)

Frontend turut diperbaiki: openEditPackageModal() sebelumnya default ke 0 saat price_quad/triple/double kosong (kasus umum untuk paket-paket lama), kini jatuh balik ke x.price terlebih dahulu.

Diverifikasi dua kali: (1) via panggilan API langsung — fee default paket & pengecualian agen sama-sama berfungsi benar; (2) via klik UI asli — buka modal Edit Paket "Paket Hemat Syawal 2026", field harga tampil benar (Rp 25.900.000, bukan 0), klik "Update Paket", lalu dicek ulang lewat API bahwa price tetap Rp 25.900.000 (tidak ter-wipe).

2. Analisis Migrasi Data Agen dari Google Sheet

Pengguna membagikan link Google Form pendaftaran konsultan (dibatasi akses, tidak bisa dibuka) dan link Google Sheet "MASTER DATA KONSULTAN UMAR" (mode Hanya Lihat) sebagai contoh nyata data yang perlu dimigrasikan ke ERP. Sheet ini ditelusuri langsung lewat Browser pane untuk memetakan strukturnya sebelum mengubah kode apapun.

2.1 Struktur Sheet yang Ditemukan

TabIsi
Form Responses 1Data mentah Google Form. Berantakan karena Google Form memakai branching logic per provinsi untuk pertanyaan "Kota/Kabupaten" — menghasilkan 30+ kolom berjudul sama, hanya satu terisi per baris sesuai provinsi responden.
MASTER DATAVersi bersih hasil konsolidasi — sumber yang relevan untuk migrasi. Kolom: No, Tanggal Pendaftaran, Nama Agen, ID (kode internal lama), Provinsi, Kab/Kota, Kecamatan, Kelurahan, Detail Alamat, Nomor WA, Akun IG, Email, Nomor Surat (perjanjian), dan 4 checklist kelengkapan marketing kit.

Kesimpulan penting: sheet ini adalah data pendaftaran konsultan/agen (bukan jamaah) — cocok untuk modul Keagenan, tapi jauh lebih kaya dari tabel agents yang lama (hanya name + phone). Pola alamatnya (Provinsi/Kab-Kota/Kecamatan/Kelurahan) identik dengan yang sudah dipakai jamaah, sehingga bisa langsung reuse konvensi penamaan kolom yang sama.

2.2 Keputusan Bersama Pengguna

✅ Perluas tabel agents yang sudah ada (bukan tabel terpisah agent_profile) — konsisten dengan pola alamat jamaah.

✅ Migrasi data historis bersifat one-time import (bukan sinkronisasi berkelanjutan dengan Google Form/Sheet) — dijadwalkan untuk nanti, tidak dieksekusi di sesi ini.

✅ Form pendaftaran agen dibangun sebagai form publik + antrian review, meniru persis pola pendaftaran_publik milik jamaah — bukan sekadar perluasan form internal admin.

3. Perluasan Struktur Data Agen

Tabel agents diperluas dengan 14 kolom baru, memakai nama kolom yang identik dengan yang sudah dipakai untuk alamat jamaah (province, city, subdistrict, village, address) supaya konsisten & bisa langsung reuse API wilayah cascading yang sama.

Dua kolom terakhir (legacy_code, registered_at) sengaja disiapkan lebih awal walau belum dipakai — akan berguna saat impor data historis benar-benar dijalankan, supaya kode agen lama dari sistem sebelumnya tetap tersimpan sebagai referensi dan tanggal daftar asli (bisa jauh di 2025) tidak tertimpa created_at yang otomatis ke-stamp saat baris benar-benar dibuat di ERP.

4. Form Pendaftaran Agen Publik & Kotak Masuk Review

Dibangun meniru persis pola pendaftaran_publik milik jamaah: calon mitra mengisi sendiri lewat link publik, data masuk ke tabel antrian (bukan langsung ke agents), lalu Admin/CS mereview sebelum resmi jadi agen aktif.

4.4 Pengujian End-to-End

Diuji penuh lewat 2 tab browser terpisah: (1) isi & kirim form publik di /daftar-agen dengan alamat DKI Jakarta → Kota Jakarta Selatan → Tebet → Tebet Barat; (2) di tab admin, badge Kotak Masuk langsung bertambah "1" secara realtime tanpa refresh; (3) klik baris → detail lengkap tampil benar; (4) klik "Terima" → modal Tambah Agen terbuka dengan seluruh 4 jenjang alamat ter-cascade otomatis (bukan cuma provinsi); (5) tambahkan Nomor Surat & centang "Banner Wide", simpan → status antrian berubah "Diterima", "Total Mitra/Agen" bertambah dari 6 → 7; (6) diverifikasi lewat API bahwa seluruh field tersimpan persis; (7) dibuka lagi lewat Edit Agen (bukan panggilan API) — seluruh field termasuk alamat cascading & checkbox kit tetap tampil benar, disimpan ulang, dan dicek API sekali lagi tidak ada data yang hilang atau berubah.

6. Catatan & Potensi Pengembangan Lanjutan

  • Impor data historis dari Google Sheet belum dijalankan. Struktur tabel & form sudah siap menampung field-fieldnya, tapi ratusan baris data konsultan lama di sheet "MASTER DATA KONSULTAN UMAR" masih perlu diproses lewat script migrasi satu-kali (rencana: export sheet ke CSV, lalu tulis script baca-&-insert) begitu pengguna siap melanjutkan.
  • Fitur "cashback/klaim referral agen" (agen membawa agen lain) yang sempat didiskusikan dibatalkan — pengguna berencana menanganinya lewat Expense Report yang sudah ada, bukan tabel/alur klaim baru.
  • Nomor Surat Perjanjian & checklist kelengkapan kit (Banner Wide/X Banner/Kartu Nama/ID Card) sengaja tidak dimasukkan ke form publik /daftar-agen — keduanya bersifat administratif internal yang diisi staff saat proses onboarding, bukan sesuatu yang diisi calon agen sendiri.
  • Data lama (177+ baris) di Google Sheet memakai skema kode ID sendiri (mis. ATRV-060120) hasil kombinasi kode provinsi + urutan — pola persis penomorannya belum sepenuhnya diformalkan, tapi tidak krusial karena ERP akan tetap memakai id auto-increment sendiri; kode lama itu hanya perlu disimpan apa adanya ke kolom referensi legacy_code saat migrasi nanti.
