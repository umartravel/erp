DOKUMEN TEKNIS UNTUK TESIS

Rancang Bangun Sistem CRM Travel Umroh Berbasis Web dengan Arsitektur Client–Server, REST API, dan Komunikasi Real-Time

Dokumentasi teknis lengkap aplikasi UMAR CRM: arsitektur, pustaka yang digunakan beserta alasannya, struktur modul, model data, desain keamanan, manajemen peran, dan justifikasi pemilihan metode dibanding alternatif lain.

Abstrak

UMAR CRM adalah aplikasi Customer Relationship Management terpadu untuk bisnis travel umroh yang mengintegrasikan empat divisi — Sales, Keuangan (Finance), Operasional (Ops), dan Manajemen (Admin) — ke dalam satu sistem berbasis web. Sistem menggantikan proses manual (catatan terpisah, banyak ponsel WhatsApp, rekap Excel) dengan satu sumber data tunggal yang tersinkronisasi secara real-time.

Aplikasi dibangun dengan arsitektur client–server: backend Python/FastAPI menyediakan REST API dan kanal WebSocket (Socket.IO), sedangkan frontend berupa Single Page Application HTML/JavaScript. Basis data menggunakan SQLite. Sistem dilengkapi automasi WhatsApp, pemeriksaan visa otomatis berbasis headless browser, mekanisme gatekeeper (SOP digital), kontrol akses berbasis peran (RBAC), serta pemodelan status multi-dimensi untuk merepresentasikan siklus hidup jamaah secara akurat.

Dokumen ini memaparkan keputusan rekayasa perangkat lunak yang diambil, lengkap dengan perbandingan terhadap metode/pustaka alternatif dan alasan pemilihannya.

1. Pendahuluan

1.1 Latar Belakang

Bisnis travel umroh memiliki alur kerja lintas-divisi yang panjang: akuisisi calon jamaah (lead), pembayaran bertahap (DP hingga lunas), pengurusan dokumen & visa, distribusi perlengkapan, hingga keberangkatan. Tanpa sistem terpadu, tiap divisi bekerja terpisah sehingga rawan kesalahan: harga paket berubah sepihak, jamaah lunas tetapi visanya tidak diproses, atau perlengkapan diserahkan padahal pembayaran belum cukup. UMAR CRM hadir untuk menutup celah tersebut melalui satu basis data bersama dan aturan SOP yang ditegakkan oleh sistem (bukan sekadar imbauan).

1.2 Tujuan Sistem

  • Menyatukan data Sales, Finance, dan Ops dalam satu sumber kebenaran (single source of truth).
  • Menegakkan SOP secara otomatis melalui mekanisme gatekeeper untuk mencegah human error dan kecurangan.
  • Mengotomasi komunikasi (invoice & pengingat WhatsApp) dan pemeriksaan visa.
  • Menyediakan pemantauan manajerial (dashboard, deteksi bottleneck, audit aktivitas).

1.3 Ruang Lingkup

Sistem mencakup modul pendaftaran & CRM, follow-up lead, keuangan & buku besar, operasional & logistik, manajemen vendor, live-chat WhatsApp multi-agen, pelaporan, serta pengaturan aplikasi. Tidak mencakup (saat ini) integrasi payment gateway nyata dan aplikasi mobile native.

Kondisi As-Is (Sebelum)

  • Data terpisah: catatan sales, Excel keuangan, ponsel WA sendiri-sendiri.
  • SOP berupa imbauan lisan — rawan harga diubah sepihak & over-booking.

  • SOP ditegakkan otomatis oleh sistem (gatekeeper) — tidak bisa di-bypass.
  • Invoice, komisi, & pengingat WA otomatis; cek visa via robot.
  • Dashboard manajerial + deteksi bottleneck + audit trail menyeluruh.

2.1 Penggabungan FastAPI + Socket.IO

Kedua kanal dijalankan dalam satu proses ASGI. Socket.IO membungkus aplikasi FastAPI sehingga request /socket.io/* ditangani oleh mesin Socket.IO, sisanya diteruskan ke FastAPI.

app.py — titik gabung ASGI 
# Gabungkan FastAPI + Socket.IO menjadi satu aplikasi ASGI.
asgi = socketio.ASGIApp(sio, other_asgi_app=app, socketio_path="socket.io")

if __name__ == "__main__":
    uvicorn.run("app:asgi", host="0.0.0.0", port=PORT, log_level="info")

Berkas statis frontend (public/) di-mount paling akhir agar route API, /panduan, dan /uploads ber-prioritas lebih tinggi daripada static handler.

4.1 Lapisan Akses Data (db.py)

Karena SQLite dipakai dari banyak thread (FastAPI threadpool + thread WhatsApp), koneksi dibuat dengan check_same_thread=False dan setiap operasi dilindungi RLock untuk mencegah race condition. Mode WAL meningkatkan konkurensi baca/tulis.

db.py — koneksi & helper 
_conn = sqlite3.connect(DB_FILE, check_same_thread=False)
_conn.row_factory = sqlite3.Row          # hasil query sebagai dict
_conn.execute("PRAGMA journal_mode=WAL") # konkurensi lebih baik
_lock = threading.RLock()

def query_all(sql, params=()):
    with _lock:
        cur = _conn.execute(sql, params)
        return [dict(r) for r in cur.fetchall()]

def execute(sql, params=()):
    with _lock:
        cur = _conn.execute(sql, params)
        _conn.commit()
        return cur.lastrowid, cur.rowcount

Pola helper ini menyembunyikan detail koneksi sehingga route di app.py cukup menulis db.query_all(...) / db.execute(...) — meniru gaya API db.all/db.run pada versi Node.js sebelumnya untuk memudahkan migrasi.

6. Desain Dimensi Status (Keputusan Inti)

Masalah: versi awal menyimpan seluruh siklus hidup jamaah dalam satu kolom status yang mencampur empat hal: tahap penjualan, pembayaran, visa, dan perjalanan. Akibatnya, ketika visa disetujui dan status menjadi "Visa Approved", informasi "Lunas" hilang — satu kolom tidak bisa menyatakan dua keadaan sekaligus.

Solusi: status dipecah menjadi empat dimensi independen, sementara kolom status lama dipertahankan sebagai cermin turunan (derived mirror) demi kompatibilitas frontend yang sudah ada.

DimensiNilai
pipeline_stageLead → Waitlisted → Registered → Booked → Cancelled
payment_statusUnpaid → DP → Lunas (→ Refunded)
visa_statusBelum Proses → Proses Kedutaan → Visa Approved
trip_statusNotStarted → OnTrip → Completed
app.py — menurunkan label kompatibel dari dimensi 
def _derive_status(pipeline, payment, visa, trip):
    if trip == "OnTrip":         return "On Trip"
    if pipeline == "Cancelled":  return "Cancelled"
    if visa == "Visa Approved":  return "Visa Approved"
    if payment == "Lunas":       return "Lunas"
    if payment == "DP":          return "DP Masuk"
    if pipeline == "Registered": return "Terdaftar"
    if pipeline == "Waitlisted": return "Waitlisted"
    return "Lead - Follow Up"

def sync_status_mirror(jid):
    j = db.query_one("SELECT pipeline_stage, payment_status, visa_status, "
                     "trip_status FROM jamaah WHERE id = ?", (jid,))
    label = _derive_status(j["pipeline_stage"], j["payment_status"],
                           j["visa_status"], j["trip_status"])
    db.execute("UPDATE jamaah SET status = ? WHERE id = ?", (label, jid))
    return label

Mengapa pola "cermin", bukan langsung mengganti kolom status? Mengganti kolom akan memaksa perubahan di puluhan titik frontend (filter, badge, tombol) sekaligus — berisiko tinggi. Dengan cermin, dimensi menjadi sumber kebenaran yang bersih (siap dipakai fitur baru & pelaporan akurat), tanpa mengubah frontend lama sama sekali. Mengapa tidak memakai pustaka state-machine? Empat dimensi ini bergerak independen (jamaah bisa Lunas tapi visa masih diproses), sehingga model multi-atribut lebih tepat daripada satu mesin status tunggal.

Hasil: setelah perubahan, ketika visa disetujui, payment_status tetap bernilai "Lunas" — bug kehilangan data tuntas, dan laporan keuangan menjadi akurat.

7. Autentikasi & Keamanan

7.1 Kata Sandi (bcrypt)

Kata sandi tidak pernah disimpan polos. bcrypt menambah salt acak & cost factor sehingga proses verifikasi sengaja lambat — menghambat serangan brute-force.

auth.py 
def hash_password(plain):  return bcrypt.hashpw(plain.encode(), bcrypt.gensalt(10)).decode()
def verify_password(plain, hashed):
    try:    return bcrypt.checkpw(plain.encode(), hashed.encode())
    except (ValueError, TypeError): return False

7.2 Token JWT (stateless)

Setelah login, server menerbitkan JWT berisi id, peran, & nama dengan masa berlaku 8 jam. Token dikirim klien di header Authorization pada tiap request; server cukup memverifikasi tanda tangan — tanpa menyimpan sesi.

auth.py — dependency RBAC FastAPI 
def authenticate_token(authorization: str = Header(default=None)) -> dict:
    token = authorization.split(" ", 1)[1] if authorization and \
            authorization.startswith("Bearer ") else None
    if not token:
        raise HTTPException(status_code=401, detail="Akses Ditolak")
    try:
        return jwt.decode(token, JWT_SECRET, algorithms=[JWT_ALGO])
    except jwt.PyJWTError:
        raise HTTPException(status_code=403, detail="Token tidak valid")

Mengapa JWT, bukan session server-side? JWT bersifat stateless — tidak perlu menyimpan state sesi di server/Redis, cocok untuk arsitektur sederhana & mudah di-scale horizontal. Pengecekan peran dilakukan oleh helper require_role(user, "admin", "finance") di setiap route sensitif.

7.3 Perlindungan Dokumen PII

Dokumen sensitif (KTP, KK, Paspor, sertifikat vaksin) & media WhatsApp disimpan di folder privat uploads_private/ di luar direktori statis publik, lalu disajikan hanya melalui route ber-autentikasi. Karena tag <img>/<a> tidak mengirim header, token boleh dikirim via query string. Serangan path traversal dicegah dengan os.path.basename.

app.py — penyajian file ber-token 
@app.get("/uploads/{filename}")
async def serve_upload(filename: str, _user=Depends(authenticate_file_token)):
    safe = os.path.basename(filename)            # cegah ../ path traversal
    path = os.path.join(UPLOAD_DIR, safe)
    if not os.path.isfile(path):
        raise HTTPException(status_code=404, detail="File tidak ditemukan")
    return FileResponse(path)

Mengapa tidak menaruh file di folder publik? Pada versi awal, dokumen berada di public/uploads sehingga siapa pun yang menebak URL dapat mengunduh paspor jamaah — pelanggaran privasi. Pemindahan ke folder privat + gerbang token menutup celah tersebut (terverifikasi: tanpa token → HTTP 401).

7.4 Gatekeeper (SOP yang ditegakkan sistem)

Selain RBAC, sistem menegakkan aturan bisnis: harga/paket terkunci setelah DP, kuota tidak boleh terlampaui, perlengkapan hanya boleh diserahkan bila pembayaran ≥ ambang (default 75%, dapat diatur), dan komisi agen cair otomatis tepat saat lunas. Aturan ini berada di sisi server (bukan hanya UI) sehingga tidak bisa di-bypass.

8. Komunikasi Real-Time (Socket.IO)

Saat satu divisi mengubah data, divisi lain perlu melihatnya tanpa me-refresh. Server mengirim event ke seluruh klien melalui Socket.IO. Karena perubahan dapat dipicu dari thread lain (mis. callback WhatsApp), helper notify() menjadwalkan emit secara aman ke event loop utama.

realtime.py — emit aman lintas-thread 
sio = socketio.AsyncServer(async_mode="asgi", cors_allowed_origins="*")

def notify(event, data=None):
    if _loop is None: return
    try:
        asyncio.run_coroutine_threadsafe(sio.emit(event, data), _loop)
    except RuntimeError:
        pass
EventArti
wa_statusStatus koneksi WhatsApp + QR pairing.
wa_new_messagePesan WhatsApp masuk/keluar baru.
wa_conversation_updatedRingkasan percakapan diperbarui.
data_updatedSinyal agar klien menyegarkan data (jamaah/transaksi/dll.).

Mengapa WebSocket, bukan polling atau SSE? Polling (klien bertanya berkala) boros bandwidth & lambat. SSE hanya satu arah (server→klien). Socket.IO memberi kanal dua arah, otomatis reconnect, dan fallback bila WebSocket diblokir — paling sesuai untuk live chat & sinkronisasi.

9. Peran Pengguna (RBAC) & Tujuannya

Administrator Super User

Tujuan: pemilik/manajemen. Akses penuh, dapat menembus gatekeeper untuk koreksi, mengelola karyawan & paket, melihat audit, dan mengatur aplikasi (logo, ambang DP).

Sales Frontliner

Tujuan: akuisisi & perawatan calon jamaah. Mendaftarkan jamaah, mencatat follow-up, melayani live chat. Hanya melihat jamaah miliknya sendiri (privasi data lintas-sales) dan dilarang mengubah harga setelah DP.

Finance Keuangan

Tujuan: verifikasi pembayaran, buku besar, payroll, deposit vendor, laporan laba-rugi. Satu-satunya yang boleh memperbarui pembayaran.

Operasional (Ops) Logistik & Visa

Tujuan: proses visa, rooming list, paspor, serah terima perlengkapan, keberangkatan, penugasan tour leader.

Pengecekan peran berlapis: di frontend menu disembunyikan sesuai peran (UX), dan di backend tiap route memanggil require_role(...) (keamanan sebenarnya). Pemisahan ini memastikan akses tidak bisa ditembus hanya dengan memanipulasi tampilan.

11. Integrasi WhatsApp

Modul whatsapp.py memakai pola Strategy: antarmuka seragam (connect, logout, get_status, send_message) dengan dua implementasi — NeonizeBackend (WhatsApp asli) dan StubBackend (cadangan). Bila pustaka neonize tidak terpasang, sistem otomatis memakai stub sehingga aplikasi tetap berjalan.

whatsapp.py — pemilihan backend 
def _get_backend():
    global _backend
    if _backend is not None: return _backend
    try:
        _backend = NeonizeBackend()        # WhatsApp asli (whatsmeow)
    except Exception:
        _backend = StubBackend()           # fallback aman (mode simulasi)
    return _backend

Mengapa pola ini? Integrasi WhatsApp adalah dependensi paling rapuh (butuh biner Go, sesi pairing). Dengan abstraksi + fallback, kegagalan WhatsApp tidak menjatuhkan seluruh CRM, dan alur dapat diuji memakai mode simulasi (WA_SIMULATE=1). Operasi pengiriman dijalankan via asyncio.to_thread agar tidak memblokir server.

13. Pengujian & Verifikasi

Verifikasi dilakukan secara end-to-end terhadap server yang berjalan:

  • Uji API: tiap endpoint dipanggil dengan token tiap peran untuk memastikan RBAC, gatekeeper, dan integritas data (mis. hapus transaksi mengembalikan paid_amount).
  • Uji alur status: satu jamaah ditelusuri dari daftar → DP → lunas → visa → berangkat, memverifikasi tiap dimensi (terbukti payment_status tetap "Lunas" setelah visa disetujui).
  • Uji keamanan file: akses dokumen tanpa token ditolak (HTTP 401), token salah (403), path traversal (404).
  • Uji antarmuka: verifikasi visual di browser sungguhan (login, halaman Pengaturan, Follow-up) — tanpa galat konsol.

16. Kesimpulan

UMAR CRM menunjukkan penerapan rekayasa perangkat lunak modern pada domain travel umroh: arsitektur client–server dengan FastAPI, komunikasi real-time Socket.IO, keamanan berlapis (bcrypt, JWT, RBAC, perlindungan PII), serta pemodelan status multi-dimensi yang akurat. Setiap keputusan teknis diambil dengan mempertimbangkan alternatif dan disesuaikan dengan kebutuhan serta skala bisnis.
