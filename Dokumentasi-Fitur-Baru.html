Fitur Baru UMAR CRM — Modul Expense Report, Peran Management, & Penguatan Audit Trail

Dokumen ini merangkum seluruh fitur, perbaikan, dan perubahan skema basis data yang dibangun dalam satu sesi pengembangan pada 15 Juli 2026. Ditulis dengan format & gaya yang sama dengan Dokumentasi-Teknis.html agar menyatu sebagai bagian dari dokumentasi teknis sistem secara keseluruhan.

Ringkasan Eksekutif

Sesi pengembangan ini berawal dari kebutuhan agar karyawan dapat mengajukan klaim penggantian biaya (reimburse) operasional, lalu berkembang menjadi sistem Expense Report penuh bergaya Odoo — dikelompokkan per Project Label (mis. "Expense Marketing 2026"), dengan alur persetujuan berjenjang, breakdown pajak per item, nomor referensi resmi, dan cetak PDF hardcopy sesuai format perusahaan.

Untuk mendukung alur persetujuan tersebut, ditambahkan peran pengguna baru: management — beserta audit menyeluruh atas hak akses lintas-modul yang sudah ada (Keuangan, Logistik, Vendor, Karyawan, Master Paket, Tactical & Audit), termasuk perbaikan sejumlah celah yang ditemukan selama proses (widget dashboard yang menyesatkan, log aktivitas yang tidak lengkap, serta bug pada mekanisme sesi login).

Seluruh fitur pada dokumen ini telah diuji langsung di browser (bukan hanya tinjauan kode) — meliputi alur penuh per role, perhitungan angka, serta pemeriksaan visual hasil PDF.

1. Modul Expense Report

Modul ini menggantikan rancangan awal "Reimburse" (klaim tunggal per baris) dengan model header + line items yang lebih formal — meniru struktur dokumen akuntansi standar (mirip modul HR Expense pada Odoo), lengkap dengan nomor referensi & kemampuan cetak hardcopy.

1.1 Mengapa Header + Line Items (bukan satu baris per klaim)?

Rancangan awal menyimpan satu klaim = satu baris (kategori + nominal + deskripsi). Ini cukup untuk reimburse sederhana, namun tidak mendukung kebutuhan nyata: satu laporan pengeluaran perjalanan/kloter biasanya berisi banyak item (bensin, konsumsi, parkir, dll.) yang diajukan & disetujui bersama-sama sebagai satu dokumen dengan satu nomor referensi. Model header (expense_reports) + baris (expense_lines) memungkinkan hal ini sekaligus memberi ruang untuk breakdown pajak per item.

1.2 Model Data

TabelFungsi & kolom kunci
expense_projectsLabel/kategori anggaran (mis. "Expense Marketing 2026"). Kolom: name (unik), is_active (nonaktif = soft-delete agar laporan lama tidak yatim), created_by.
expense_reportsHeader laporan. Kolom kunci: ref (nomor referensi unik), project_id, user_id/user_name (pengaju), period_from/period_to, approver_id/approver_name, note + note_visibility (public/private), status, validation_date, reviewed_by, review_note, paid_by/paid_at, transaction_id (tautan ke Buku Kas).
expense_linesItem pengeluaran per laporan. Kolom: report_id, date, category ("Type"), description, unit_price_net (harga sebelum pajak), tax_percent (default 11%), qty, receipt_url (opsional, foto struk).
db.py — skema tabel inti 
CREATE TABLE IF NOT EXISTS expense_reports (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ref TEXT UNIQUE,
    project_id INTEGER,
    user_id INTEGER, user_name TEXT,
    period_from TEXT, period_to TEXT,
    approver_id INTEGER, approver_name TEXT,
    note TEXT, note_visibility TEXT DEFAULT 'public',
    status TEXT DEFAULT 'Draft',
    validation_date DATETIME,
    reviewed_by TEXT, review_note TEXT,
    paid_by TEXT, paid_at DATETIME, transaction_id INTEGER,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
CREATE TABLE IF NOT EXISTS expense_lines (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    report_id INTEGER,
    date TEXT, category TEXT, description TEXT,
    unit_price_net INTEGER, tax_percent REAL DEFAULT 11, qty INTEGER DEFAULT 1,
    receipt_url TEXT, created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

1.3 Alur Status (Maker-Checker)

Menerapkan pola maker-checker: pemohon (maker) membuat & mengajukan, penyetuju (checker) memvalidasi, dan pencairan dana dilakukan pihak ketiga (finance) — tidak ada satu peran yang bisa mengajukan sekaligus mencairkan dana untuk dirinya sendiri.

Draft

Pemohon

Header dibuat (pilih Project, periode, approver, note). Baris item ditambah/dihapus bebas. Bisa di-Modify, Clone, atau Delete selama masih Draft.

Submitted

Sistem

Diajukan lewat tombol "Ajukan (Submit)" — mensyaratkan minimal 1 item & approver sudah dipilih. Header & baris terkunci (tidak bisa diedit lagi).

Approved / Rejected

admin, management

Approver menyetujui (mengisi validation_date otomatis) atau menolak dengan alasan wajib diisi (divalidasi server, bukan hanya UI).

Paid

admin, finance

Hanya dapat dibayar dari status Approved. Saat dibayar, total (incl. pajak) otomatis dicatat sebagai transaksi expense kategori expense_report di Buku Kas.

1.4 Perhitungan Pajak per Baris

Setiap baris menyimpan harga sebelum pajak (unit_price_net) & persentase pajak sendiri (default 11%, dapat diubah per baris) — bukan satu tarif pajak global — karena tiap item pengeluaran bisa punya perlakuan pajak berbeda.

app.py — kalkulasi total per baris & total laporan 
def _line_totals(line):
    net = (line["unit_price_net"] or 0) * (line["qty"] or 0)
    tax = round(net * (line["tax_percent"] or 0) / 100.0)
    return net, tax, net + tax

def _report_totals(lines):
    net = tax = 0
    for ln in lines:
        n, t, _ = _line_totals(ln)
        net += n; tax += t
    return net, tax, net + tax

Total laporan (Amount excl. tax / tax / incl. tax) selalu dihitung ulang dari baris-baris yang ada (bukan disimpan sebagai kolom terpisah yang bisa kadaluarsa) — menjamin angka selalu konsisten dengan data terbaru.

1.5 Nomor Referensi

Format EXP/<tahun>/<urutan 4-digit>, dihasilkan otomatis berdasarkan jumlah laporan yang sudah dibuat pada tahun berjalan.

app.py — generator nomor referensi 
def _generate_expense_ref():
    year = datetime.datetime.now().year
    row = db.query_one(
        "SELECT COUNT(*) as c FROM expense_reports WHERE ref LIKE ?", (f"EXP/{year}/%",)
    )
    seq = (row["c"] if row else 0) + 1
    return f"EXP/{year}/{seq:04d}"   # contoh: EXP/2026/0001

1.6 Cetak PDF (Hardcopy)

PDF dibangkitkan dengan pustaka reportlab (expense_pdf.py, modul terpisah mengikuti pola pemisahan tanggung jawab yang sama dengan visa_checker.py/whatsapp.py). Layout dirancang meniru dokumen resmi ala Odoo atas permintaan pengguna: kop surat (logo + identitas perusahaan), dua kotak info (perusahaan & laporan), tabel item, kotak total, dan nomor halaman.

Mengapa reportlab, bukan library lain (WeasyPrint, wkhtmltopdf)? WeasyPrint & wkhtmltopdf butuh dependensi sistem/biner eksternal (GTK, Qt WebKit) yang rawan gagal terpasang di Windows — sebagaimana sempat dialami saat memasang neonize/greenlet pada Python versi baru (lihat §15.2 & §3 di Dokumentasi-Teknis.html). reportlab adalah pure-Python, terbukti terpasang mulus tanpa perlu Visual C++ Build Tools.

1.7 Iterasi Desain: Rekening Karyawan → Field Note

Versi pertama PDF menampilkan info rekening pencairan dari profil karyawan (kolom phone/bank_account baru di tabel users). Setelah diuji, ditemukan keterbatasan: tidak semua expense report dicairkan ke rekening pemohon — kadang dananya untuk vendor/mitra pihak ketiga.

Solusinya: field tersebut dihapus (bukan dibiarkan menggantung tak terpakai), dan baris info pencairan di PDF diganti mengambil dari Note pada header laporan — field bebas yang sudah ada, sehingga pemohon dapat menuliskan rekening tujuan apa pun yang relevan untuk laporan tersebut. Ini adalah contoh keputusan desain yang dikoreksi berdasarkan masukan pengguna setelah demo hasil awal.

2. Peran Baru: management

Sistem RBAC sebelumnya hanya mengenal empat peran (admin, sales, finance, ops — lihat §9 Dokumentasi-Teknis.html). Kebutuhan approval Expense Report memerlukan lapisan persetujuan independen dari admin (agar admin tidak merangkap sebagai satu-satunya penyetuju), sehingga ditambahkan peran management.

Management Approver & Pengawas

Tujuan: menyetujui/menolak Expense Report secara independen dari admin; memantau kondisi kas & audit trail; melihat (bukan mengelola) data operasional lintas-divisi untuk pengambilan keputusan.

2.1 Matriks Hak Akses

Akses diberikan bertahap mengikuti permintaan eksplisit pengguna di sepanjang sesi ini — setiap penambahan diverifikasi langsung di browser sebelum dianggap selesai.

'<button>...' : '').

3. Audit Trail — Presisi Data & Fitur Pencarian

3.1 Masalah yang Ditemukan

Tabel audit_logs semula hanya menyimpan user_name (teks bebas) — dua karyawan dengan nama sama akan ambigu di log. Selain itu, sejumlah endpoint tulis penting tidak pernah mencatat log sama sekali: pembuatan/penghapusan akun karyawan, pembuatan/penghapusan paket, penugasan staf, unggah dokumen PII, dan cek visa.

3.2 Perbaikan

db.py — kolom presisi baru 
ALTER TABLE audit_logs ADD COLUMN user_id INTEGER;
ALTER TABLE audit_logs ADD COLUMN role TEXT;
app.py — log_action() menerima objek user utuh, bukan sekadar nama 
def log_action(user, action, details):
    db.execute(
        "INSERT INTO audit_logs (user_id, user_name, role, action, details) VALUES (?, ?, ?, ?, ?)",
        (user["id"], user["name"], user["role"], action, details),
    )
    notify("data_updated", "audit")

Delapan endpoint yang sebelumnya tidak ter-log kini mencatat aktivitas: CREATE_USER, DELETE_USER, CREATE_PACKAGE, DELETE_PACKAGE, UPDATE_PACKAGE_STAFF, UPLOAD_DOCUMENT, CHECK_VISA, CREATE_AGENT — ditambah rangkaian aksi baru untuk Expense Report (CREATE_EXPENSE_REPORT, SUBMIT_EXPENSE_REPORT, APPROVE_/REJECT_EXPENSE_REPORT, PAY_EXPENSE_REPORT, CLONE_EXPENSE_REPORT, DELETE_EXPENSE_REPORT) dan Project Label (CREATE_/UPDATE_/DEACTIVATE_EXPENSE_PROJECT).

3.3 Pencarian & Filter (Frontend)

Ditambahkan kolom pencarian bebas teks & dropdown filter per-karyawan di halaman Tactical & Audit, memfilter data yang sudah ada di sisi klien (tanpa fetch ulang) agar responsif.

public/index.html — filter client-side 
function renderAuditTable() {
    const q = (document.getElementById('audit-search')?.value || '').toLowerCase();
    const selUser = document.getElementById('audit-filter-user')?.value || '';
    const filtered = auditLogsCache.filter(a => {
        if (selUser && a.user_name !== selUser) return false;
        if (q && !`${a.user_name} ${a.action} ${a.details}`.toLowerCase().includes(q)) return false;
        return true;
    });
    // ...render filtered ke tabel
}

Catatan teknis: input pencarian awalnya memakai event onkeyup, namun terbukti tidak konsisten terpicu oleh sebagian metode simulasi input (termasuk saat pengujian otomatis). Diganti ke oninput, yang menangkap seluruh perubahan nilai (ketik, tempel, maupun pengisian terprogram) secara lebih andal.

4. Keagenan — Widget "Agen Terbaik"

Menyusul perbaikan serupa pada widget "Sales Terbaik" (§4.1), halaman Keagenan (Mitra) diberi kartu statistik & kolom performa nyata, bukan sekadar daftar agen statis.

4.1 Masalah pada Widget "Sales Terbaik" (Perbaikan Terkait)

Leaderboard sales di-sort menurun berdasarkan jumlah konversi, lalu frontend menampilkan elemen pertama sebagai "Sales Terbaik" — tanpa memeriksa apakah nilainya benar-benar > 0. Saat hanya ada satu sales dan datanya masih kosong, sistem tetap menampilkan namanya sebagai "terbaik", padahal belum ada prestasi sama sekali.

public/index.html — perbaikan (before → after disingkat) 
// Sebelum: card('Sales Terbaik', lb[0] ? lb[0].name : '-', ...)
// Sesudah:
const bestSales = lb[0];
card('Sales Terbaik', (bestSales && bestSales.converted > 0) ? bestSales.name : '-', 'award', 'amber');

4.2 Endpoint Performa Agen

Endpoint baru mengagregasi jumlah jamaah aktif (di luar status Lead & Cancelled) per agen, memakai LEFT JOIN agar agen tanpa jamaah tetap tampil di tabel (dengan angka 0) namun otomatis tersingkir dari posisi "terbaik".

app.py 
@app.get("/api/agents/performance")
async def agents_performance(user=Depends(authenticate_token)):
    board = db.query_all(
        "SELECT a.id, a.name, a.phone, a.commission_fee, "
        "COUNT(CASE WHEN j.status NOT IN ('Cancelled', 'Lead - Follow Up') THEN j.id END) as total_jamaah "
        "FROM agents a LEFT JOIN jamaah j ON a.id = j.agent_id "
        "GROUP BY a.id ORDER BY total_jamaah DESC, a.name ASC", ()
    )
    return {"leaderboard": board}

Halaman Keagenan kini menampilkan 3 kartu (Total Mitra/Agen, Jamaah dari Mitra, Agen Terbaik) serta kolom "Jamaah Terkirim" pada tabel — konsisten dengan widget "Top Mitra/Agen Aktif" yang sudah ada di Dashboard, namun dengan cakupan data lebih lengkap (bukan hanya top 5).

5. Perbaikan Keamanan & Bug

5.1 authFetch Memaksa Logout pada 403 (Ditemukan Saat Uji Peran Management)

Saat memperluas akses view-only role management ke berbagai halaman (§2), ditemukan bahwa helper authFetch di frontend memperlakukan 401 (sesi tidak valid) dan 403 (peran tidak berwenang) secara identik — keduanya memicu logout paksa. Ini berbahaya: satu tombol tulis yang belum sempat disembunyikan untuk role tertentu dapat membuat pengguna terlempar keluar dari aplikasi hanya karena mengklik sesuatu yang tidak diizinkan untuknya.

public/index.html — sebelum vs sesudah 
// Sebelum:
if (res.status === 401 || res.status === 403) { logout(); throw new Error('Akses ditolak atau sesi berakhir'); }

// Sesudah — 403 tidak lagi logout, cukup lempar error (ditangkap & ditampilkan sebagai toast):
if (res.status === 401) { logout(); throw new Error('Sesi berakhir, silakan login kembali'); }
if (!res.ok) {
    let errData; try { errData = await res.json(); } catch(e) {}
    throw new Error((errData && errData.error) ? errData.error : `Kesalahan Sistem (${res.status})`);
}

Perbaikan ini berlaku untuk seluruh sistem (bukan hanya modul baru) — memperbaiki kekokohan (robustness) aplikasi secara umum terhadap kombinasi peran & endpoint di masa depan.

5.2 Visibilitas Note (Public/Private) pada Expense Report

Field note_visibility pada laporan menentukan siapa yang boleh membaca note saat laporan tampil di daftar/list — bila "private", hanya pemilik, approver, atau admin/management/finance yang melihat isinya; pihak lain melihat field kosong. Pada endpoint unduh PDF, pemeriksaan ini tidak diterapkan ulang secara sengaja: siapa pun yang lolos _assert_report_access() (pemilik atau admin/management/finance) sudah tentu berwenang, sehingga PDF selalu menampilkan Note apa adanya.

8. Catatan & Potensi Pengembangan Lanjutan

  • Kolom expense_lines.receipt_url (foto struk per item) sudah ada di skema & endpoint, namun belum ditautkan ke elemen upload file di form tambah item — dapat diaktifkan menyusul pola yang sama seperti Document Vault jamaah.
  • Fitur reimburse versi pertama (klaim tunggal, tabel reimbursements) sudah sepenuhnya digantikan Expense Report; tabel lama dibiarkan ada di berkas basis data (tidak di-drop) sebagai jejak historis, namun tidak lagi direferensikan kode manapun.
  • Halaman Manajemen Vendor untuk role management saat ini murni lihat-saja; bila di kemudian hari management perlu mengajukan kontrak vendor (bukan hanya menyetujuinya via Expense Report), endpoint POST /api/procurement perlu diperluas require_role-nya.
  • Nomor referensi Expense Report (EXP/tahun/urutan) dihitung dari COUNT(*) per tahun — cukup untuk skala saat ini; bila laporan pernah dihapus di tengah urutan, nomor tidak akan pernah bentrok (unik di kolom ref) namun urutannya bisa terlihat tidak berurutan sempurna.
