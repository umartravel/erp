Fitur Baru UMAR CRM — Atribusi CS, Manajemen Akun, & Foto Profil

Dokumen ini merangkum seluruh fitur, perbaikan, dan perubahan skema basis data yang dibangun dalam satu sesi pengembangan pada 23 Juli 2026. Ditulis dengan format & gaya yang sama dengan Dokumentasi-Fitur-22-Juli-2026.html agar menyatu sebagai bagian dari dokumentasi teknis sistem secara keseluruhan.

Ringkasan Eksekutif

Sesi ini dimulai dari diskusi seputar form pendaftaran publik: pengguna ingin setiap jamaah punya CS (Customer Service) tujuan yang jelas — sebelumnya sales_id selalu otomatis diisi siapa pun karyawan yang klik "Terima", tidak peduli preferensi calon jamaah. Solusinya: dropdown "Pilih CS" opsional di form publik, yang diteruskan sampai ke atribusi sales_id final. Fitur yang sama kemudian di-mirror penuh untuk modul Keagenan (mitra/agen) atas permintaan eksplisit pengguna, termasuk metrik baru "Agen Direkrut" di leaderboard performa Sales.

Pengguna lalu bertanya sederhana — "kenapa tidak bisa edit juga?" — yang membongkar gap nyata: halaman Kelola Pengguna cuma bisa Tambah & Hapus karyawan, tidak pernah punya endpoint Edit sejak awal. Ini berkembang jadi paket fitur Manajemen Akun penuh: Profil Saya (self-service data diri), Ganti Password (karyawan bisa ganti sendiri, Admin bisa reset siapa saja), dan Edit Karyawan oleh Admin (data akun + data profil).

Permintaan "tambahkan juga foto profil buat testing" membuka bug nyata: foto yang diupload tidak tampil sama sekali di mana pun karena disimpan di folder privat yang butuh token otentikasi, sedangkan kode menampilkannya lewat background-image biasa tanpa token — langsung diperbaiki. Sesi ditutup dengan permintaan berturut-turut untuk menyebarkan foto profil ke semua tempat yang menampilkan nama karyawan/CS — total menjangkau 9 area berbeda di seluruh aplikasi, dari sidebar sampai Audit Trail.

1. Atribusi CS untuk Jamaah

Kolom jamaah.sales_id sudah ada sejak lama untuk RBAC (Sales hanya lihat jamaah miliknya) dan statistik performa — tapi nilainya selalu otomatis diisi user["id"] milik siapa pun yang klik "Terima" di Kotak Masuk Pendaftaran, tidak pernah mencerminkan preferensi calon jamaah sendiri.

1.1 Dropdown "Pilih CS" di Form Publik

Endpoint publik baru (tanpa auth, karena diakses calon jamaah sebelum login) mengembalikan daftar karyawan dengan role = 'sales':

app.py — endpoint publik daftar CS 
@app.get("/api/public/cs-list")
async def public_cs_list():
    return db.query_all("SELECT id, name FROM users WHERE role = 'sales' ORDER BY name ASC", ())

Field ini opsional — kalau calon jamaah tidak memilih, perilaku lama tetap berlaku (CS yang menerima). preferred_cs_id disimpan di pendaftaran_publik, lalu saat "Terima" diproses, jamaah_create membaca ulang preferensi itu untuk menentukan sales_id final — bukan langsung memakai id karyawan yang sedang login.

1.2 Kolom & Filter CS di Database Jamaah

Gap yang ditemukan lewat pertanyaan pengguna: tidak ada tempat untuk melihat CS mana yang menangani jamaah tertentu, apalagi memfilternya. Opsi filter sengaja diturunkan dari data jamaah yang sudah dimuat di klien (bukan panggil /api/users), karena endpoint itu dibatasi admin/management sementara Sales — pengguna utama halaman ini — perlu tetap bisa memakai filter.

public/index.html — turunan opsi filter dari data yang sudah ada 
const csMap = new Map();
allJamaah.forEach(j => { if (j.sales_id && j.sales_name) csMap.set(j.sales_id, j.sales_name); });

1.3 Pengujian End-to-End

Disimulasikan penuh: submit form publik memilih "Tim Sales" sebagai CS → login sebagai Administrator → klik "Terima & Lengkapi Data" → dicek lewat API, hasil jamaah.sales_id mengarah ke Tim Sales (id 2), bukan Administrator (id 1) yang memproses. Filter CS di Database Jamaah dikonfirmasi menyaring tabel dengan benar dan reset ke "Semua CS" mengembalikan semua baris.

2. Atribusi CS untuk Keagenan (Mirror Pola Jamaah)

Pengguna secara eksplisit meminta pola yang persis sama diterapkan ke modul Keagenan, untuk atribusi kinerja rekrut mitra/agen — bukan sekadar informasi kontak.

2.1 Skema & Alur

db.py — kolom baru 
ALTER TABLE agents ADD COLUMN handler_cs_id INTEGER;
ALTER TABLE pendaftaran_agen_publik ADD COLUMN preferred_cs_id INTEGER;

Form pendaftaran agen publik (/daftar-agen) dapat dropdown "Pilih CS" yang me-reuse endpoint /api/public/cs-list yang sama dengan form jamaah. Saat "Terima" diproses lewat agents_create, handler_cs_id default ke karyawan yang klik Terima, kecuali submission publik punya preferred_cs_id.

2.2 Metrik Baru: "Agen Direkrut"

Karena tujuannya atribusi kinerja (bukan sekadar tampilan), fungsi _sales_stats() — yang sebelumnya murni berbasis tabel jamaah untuk leaderboard performa Sales — diperluas dengan hitungan agen yang direkrut per CS:

app.py — _sales_stats() 
agents_recruited = db.query_one(
    "SELECT COUNT(*) c FROM agents WHERE handler_cs_id = ?", (sales_id,)
)["c"]

Kartu "Agen Direkrut" muncul di halaman Follow-up Lead, baik untuk statistik diri sendiri (role Sales) maupun leaderboard gabungan (role Admin). Diuji: submit form agen publik memilih "Tim Sales" → Administrator klik Terima → dicek lewat API, handler_cs_id agen baru mengarah ke Tim Sales; login sebagai Tim Sales, kartu "Agen Direkrut" menunjukkan angka 1 yang sesuai.

3. Manajemen Akun: Profil Saya, Ganti Password, Edit Karyawan

Dipicu diskusi soal setiap karyawan mendata dirinya sendiri, lalu ganti password, lalu satu pertanyaan singkat pengguna — "kenapa tidak bisa edit juga?" — yang membongkar gap: halaman Kelola Pengguna sejak awal cuma bisa Tambah & Hapus, tidak pernah ada endpoint Edit.

3.1 Kolom Profil Baru di users

db.py — kolom profil diri 
ALTER TABLE users ADD COLUMN phone TEXT;
ALTER TABLE users ADD COLUMN personal_email TEXT;
ALTER TABLE users ADD COLUMN address TEXT;
ALTER TABLE users ADD COLUMN nik TEXT;
ALTER TABLE users ADD COLUMN birth_date TEXT;
ALTER TABLE users ADD COLUMN photo_url TEXT;
ALTER TABLE users ADD COLUMN last_education TEXT;
ALTER TABLE users ADD COLUMN education_major TEXT;
ALTER TABLE users ADD COLUMN education_institution TEXT;

Field pendidikan sengaja dibuat ringkas (jenjang/jurusan/institusi, bukan riwayat multi-entri) sesuai konfirmasi pengguna — cukup untuk kebutuhan Management melihat profil karyawan, tanpa kompleksitas CV lengkap.

3.2 Ganti Password: Self-Service vs Admin Reset

Dua jalur berbeda dikonfirmasi lewat diskusi: karyawan bisa ganti password sendiri (perlu verifikasi password lama), sedangkan Admin bisa reset password siapa saja tanpa perlu tahu password lama.

app.py — dua endpoint terpisah 
@app.put("/api/users/me/password")   # self-service, verifikasi password lama
@app.put("/api/users/{uid}/reset-password")   # admin-only, tanpa password lama

Diuji: ganti password dengan password lama yang salah → ditolak (400); dengan password lama benar → berhasil, dikonfirmasi lewat percobaan login ulang dengan password baru (berhasil). Admin reset password dipakai sekaligus untuk mengembalikan password test ke semula, dan login ulang dikonfirmasi tetap berhasil.

3.3 Gap Ditemukan: Tidak Ada Endpoint Edit Karyawan

Konfirmasi lewat pengecekan kode langsung: GET/POST/DELETE /api/users sudah ada sejak awal, tapi tidak pernah ada PUT /api/users/{id}. Satu-satunya cara memperbaiki data karyawan yang salah adalah hapus lalu buat ulang. Pengguna memilih cakupan edit "data akun + data profil (semua field)".

app.py — endpoint baru 
@app.put("/api/users/{uid}")
async def users_update(uid: int, body: dict = Depends(json_body), user=Depends(authenticate_token)):
    require_role(user, "admin")
    # update username, name, role, base_salary + seluruh field profil -- TIDAK menyentuh password

Modal "Tambah User" diperluas jadi dual-mode (Tambah/Edit): field password disembunyikan & tidak wajib saat mode Edit, karena ganti password sudah ditangani jalur terpisah. Diuji: edit No. HP milik "Tim Sales" sebagai Admin → tersimpan benar, tabel refresh otomatis; login ulang sebagai sales1 dengan password lama tetap berhasil, membuktikan endpoint edit tidak menyentuh/merusak password.

4. Foto Profil: Upload, Bug Token, & Penyebaran ke 9 Area

Permintaan "coba tambahkan foto profil buat testing juga" langsung membongkar bug nyata sebelum fitur ini bisa dianggap selesai.

4.1 Bug Ditemukan: Foto Tidak Tampil Sama Sekali

Setelah upload berhasil (API mengembalikan 200 OK dengan photo_url benar), foto tetap tidak muncul di UI — hanya warna latar default. Penyebabnya: foto disimpan di folder privat (UPLOAD_DIR, sama seperti dokumen KTP/paspor) yang butuh token otentikasi untuk diakses, tapi kode menampilkannya lewat background-image: url(...) polos — browser tidak mengirim header Authorization untuk permintaan gambar semacam itu.

Solusinya sudah ada di kodebase (dipakai untuk dokumen KTP/paspor jamaah): helper fileUrl() yang menyisipkan token lewat query string.

public/index.html — helper avatar terpusat 
const setAvatarEl = (el, name, photoUrl) => {
    if (photoUrl) { el.style.backgroundImage = `url('${fileUrl(photoUrl)}')`; el.innerText = ''; }
    else { el.innerText = (name || '?').charAt(0).toUpperCase(); }  // fallback huruf inisial
};

Diverifikasi dengan mengupload 2 foto berwarna berbeda secara berurutan (hijau lalu biru) — sebelum perbaikan, keduanya tampil sebagai warna default; sesudah perbaikan, warna terakhir (biru) tampil benar di semua tempat tanpa perlu reload halaman.

4.2 Endpoint Direktori Lintas-Role

Untuk menampilkan foto CS di Live Chat (dipakai role Sales, bukan cuma Admin/Management), dibutuhkan endpoint ringan yang bisa diakses semua role tanpa membocorkan data HR sensitif:

app.py — direktori nama+foto saja 
@app.get("/api/users/directory")
async def users_directory(user=Depends(authenticate_token)):
    return db.query_all("SELECT name, photo_url FROM users", ())

4.3 Penyebaran ke 9 Area Aplikasi

Atas permintaan berturut-turut ("tambahkan juga di halaman lain yang relevan"), avatar foto (dengan fallback huruf inisial) disebar ke setiap tempat yang menampilkan nama karyawan/CS, memakai helper picAvatarHtml() yang sama:

Setiap area diuji dengan klik sungguhan di browser (bukan cuma tinjauan kode); seluruhnya mengembalikan avatar yang benar tanpa error konsol maupun server.

6. Catatan & Potensi Pengembangan Lanjutan

  • Atribusi CS untuk agen saat ini hanya dihitung sebagai jumlah ("Agen Direkrut") — belum menghitung kontribusi performa jamaah yang didatangkan lewat agen tersebut ke skor CS yang merekrutnya (sempat didiskusikan, disepakati cukup jumlah dulu).
  • Detail Expense Report (modal, bukan tabel daftar) belum menampilkan avatar untuk field "User" & "User responsible for approval" — baru tabel daftar utama yang diperbarui.
  • Kolom company_assets.assigned_to (siapa memegang aset) sengaja belum diberi avatar karena bisa berisi nama non-karyawan; hanya field "Riwayat Perpindahan · oleh [nama]" (selalu karyawan sistem) yang diberi avatar.
  • Endpoint /api/users/directory mengembalikan foto seluruh karyawan ke semua role yang login — cukup aman karena hanya nama+foto (tanpa data HR sensitif), tapi perlu diingat saat menambah field baru ke endpoint ini di kemudian hari agar tidak tidak sengaja membocorkan data lain.
